# Live session V2 contract

Implementation prepared for auth/schema review. Migration has not been applied and no deployment is claimed.

## Session

`{id, activity, audience, scorebookId, teamScopeId, title, expiresAt, canPublish, isOwner}`.

Activity is `league | prebowl | practice | social`; audience is `team | invited`. IDs are UUIDs. Nullable scorebookId is required only for competitive activity. Nullable teamScopeId is required only for team audience and identifies an existing authorized scorebook membership scope. Titles are plain text, at most 100 characters. Only the owner publishes a camera. No microphone, metadata updates, or data-channel publishing are granted.

- `GET /api/live/v2/sessions` returns `{sessions, configured}`. Only active authorized sessions are included. This collection includes sessions waiting for their first camera.
- `POST /api/live/v2/sessions` accepts `{activity,audience,title,scorebookId?,teamScopeId?,durationMinutes?}`. Duration is 5 through 480 minutes, default 120. Returns `{session}` with HTTP 201.
- `GET /api/live/v2/sessions/[id]` returns `{session}`. Use this for access rechecks, not token issuance.
- `PATCH /api/live/v2/sessions/[id]` accepts `{ended:true}`. Owner only. Returns `{ended:true,disconnected:boolean}`. Session ending is durable first; media eviction is attempted separately. False means that eviction could not be confirmed.
- `POST /api/live/v2/sessions/[id]/token` accepts `{mode:'watch'|'publish'}` and returns `{serverUrl,participantToken,connectionId}`. Each attempt gets an independent participant identity and connection ID. The session is capped at 200 issued connections; access rechecks must not mint new tokens. Initial token TTL is at most 120 seconds and never beyond remaining session duration.
- `POST /api/live/v2/sessions/[id]/invites` accepts `{email}`; owner only for invited audience. Returns `{invited:true}`. This records permission, not email delivery. Match is case-insensitive against the verified account email. Invitees to competitive footage still need access to the underlying scorebook. Maximum 50 invitations per session.

Creators must be confirmed authenticated teammates. Competitive creation requires scorebook editor/owner access and matching authoritative scorebook metadata (prebowl for pre-bowl, match without prebowl for league). Every competitive request rechecks scorebook membership, including owner requests. An invite cannot expose competitive footage to somebody without its scorebook access. Legacy unclaimed/public-link access is rejected. Session owners have access to their own invited noncompetitive session; all team viewers, including owners, require membership in teamScopeId, invited viewers require an exact verified-email invitation.

## Health

`POST /api/live/v2/sessions/[id]/health` accepts:

```json
{"connectionId":"UUID","received":[{"trackSid":"TR_example","frames":30,"bytes":100000}],"outgoing":{"frames":30,"bytes":100000}}
```

Report **interval deltas**, normally every five seconds. Report zeros when stalled; never repeat lifetime totals as if they were new media. `outgoing` is optional and only valid on a publishing connection currently publishing a camera. Counters are integer 0 through 1,000,000,000; at most 16 unique received tracks, all current unmuted server-listed camera tracks and none owned by this connection. Connection must belong to the authenticated user and this session, remain unexpired, and correspond to a currently present server participant. Returns `{accepted:true}`.

`GET /api/live/v2/sessions/[id]/health` returns:

```json
{"connections":2,"connectedCount":3,"cameraCount":1,"receivingCount":1,"observedAt":"ISO8601","evidence":"client-reported"}
```

`connectedCount` is current server participants. `connections` is participants with a fresh connection-bound client report (at most 15 seconds old). `receivingCount` is fresh reporters with positive frame and byte deltas on a currently available camera. These are self-reported observations correlated with the actual room roster, not independent proof that another human saw a picture. Responses omit participant identities, invite emails, user IDs, raw metrics, and credentials. No media is stored.

## Client lifecycle and failure semantics

All responses are private/no-store. Errors are `{error:string}` with 400 invalid input, 401 sign-in, 403 permission/origin, 404 unavailable private session/connection, 409 connection not currently in room, 413 size, 429 rate limit, or 503 unavailable service. Never display upstream credentials or errors.

Clients must recheck session access every 30 seconds, disconnect on failed access verification, disconnect at expiresAt, and stop camera/media when leaving or backgrounding. Token expiry alone does not terminate existing room participants. Server ending attempts room deletion, but access revocation or service outages otherwise rely on the compliant client recheck. This is a documented limitation, not immediate server-enforced revocation.

The existing V1 token and discovery APIs remain unchanged. `/studio` proxy access for invited confirmed nonteammates requires a separately reviewed narrow shell exception; all data handlers enforce invitations. No public session endpoint is provided.

## Storage and verification

Migration `web/supabase/migrations/202609130001_live_sessions_v2.sql` creates three service-role-only RLS tables. Session duration/activity/scope constraints are enforced in SQL as well as input validation. Connections and invitations cascade with session deletion. Expired rows remain for now; no unattended deletion or retention job is installed.

`bun test tests/live-v2.test.ts` runs isolated mocked-auth, mocked-storage and mocked-LiveKit checks against the actual handler. JWTs are signed only with fixture keys and decoded to inspect camera-only grants. Tests cover access, CSRF, creation bounds, invitations, expiry, ending, revoked competitive access, rate limits, active participant validation, stale health, cross-user/cross-session reports, and counter/track validation. No real account, database, or video service is called.
